# ANL Loader 与 Zephyr LLEXT 对比：面向资源受限 MCU 的轻量化设计

## 1. 结论

`private-loader` 分支中的 ANL Loader 并不是 Zephyr LLEXT 的完整替代品，而是一个针对
资源受限 MCU、固定架构和受控模块接口设计的最小原生代码加载方案。

其核心思路是：

> 将 ELF 解析、格式转换和大部分链接复杂度前移到 PC 端，只在 MCU 上保留格式校验、
> 连续内存装载、必要重定位、受控符号解析和入口执行。

因此，ANL Loader 优先追求最小代码体积、较低运行时开销和可预测的加载路径；Zephyr
LLEXT 则优先提供标准 ELF 支持、通用扩展管理和完整生命周期能力。

## 2. 核心差异

| 维度 | ANL Loader | Zephyr LLEXT |
| --- | --- | --- |
| 输入格式 | 自定义精简 ANL 格式 | 标准 ELF |
| 复杂度位置 | PC 端预处理，MCU 端最小加载 | MCU 端完成通用 ELF 加载和链接 |
| MCU 端实现 | 校验、复制、少量重定位、符号白名单、入口调用 | ELF 节处理、符号链接、内存区域管理、扩展注册和生命周期管理 |
| 内存分配 | 当前实现一次连续 `k_malloc()` | 按代码、数据和元数据等区域进行管理 |
| 模块生命周期 | 当前为加载、执行、返回后释放 | 支持注册、查找、调用、遍历和卸载 |
| 符号机制 | 固定导出白名单，字符串线性查找 | 内建导出表、扩展符号表、SLID 等机制 |
| 适用范围 | 单板、单架构、小模块、受控 ABI | 多架构、通用 Zephyr 动态扩展 |

## 3. ANL Loader 的轻量级优势

### 3.1 MCU 无需解析完整 ELF

ANL 文件只保留模块运行所需的信息：

- 32 字节固定文件头；
- 24 字节固定节头；
- CODE、RODATA、DATA 和 BSS；
- 精简符号表、字符串表和重定位表；
- 入口偏移和 CRC-32。

编译器仍然生成标准 ELF 目标文件，但 `tools/anl_link.py` 在 PC 端使用 `pyelftools` 将
`.o` 转换为 `.anl`。调试信息和 MCU 加载阶段不需要的 ELF 信息不会进入设备端解析路径。

ANL 的优势不是在 MCU 上实现一个更小的通用 ELF Loader，而是让 MCU 不再承担完整 ELF
解析和通用动态链接的复杂度。

### 3.2 Loader 代码规模小

当前实现的源代码规模为：

- `anl_loader.c`：187 行，约 6.8 KB 源文件；
- `anl_loader.h`：98 行，约 2.1 KB 源文件；
- `tools/anl_link.py`：214 行，PC 端处理逻辑不占用 MCU 固件空间。

在当前 `qemu_cortex_m3` 示例构建中，`anl_loader.c.obj` 的代码段约为 **1061 字节**。
链接映射中，`anl_validate()` 约为 120 字节，`anl_load()` 约为 668 字节。

这些数字用于说明当前原型的实现量级，不应被解释为所有平台上启用 ANL 后固件只增加
1061 字节。最终增量还会受到编译优化、目标架构以及 `printk`、heap、`memcpy`、`strcmp`
等公共依赖是否已被固件使用的影响。

### 3.3 加载路径短且可预测

当前加载流程只有以下主要步骤：

1. 检查 magic、版本、文件大小和 CRC-32；
2. 统计所有可分配节的总大小；
3. 一次性申请连续内存；
4. 复制代码和初始化数据，并清零 BSS；
5. 遍历重定位项并修补指令或地址；
6. 从宿主导出白名单中解析外部符号；
7. 跳转到模块入口；
8. 入口返回后释放模块内存。

它不维护通用扩展注册表、引用关系、检查元数据、多个 Loader 后端或复杂生命周期状态，
因此控制流更容易审计，加载时间和峰值内存也更容易估算。

### 3.4 运行时内存模型简单

ANL Loader 将所有 `SHF_ALLOC` 节合并到一次连续分配中，逻辑布局为：

```text
CODE | RODATA | DATA | BSS
```

入口执行完毕后整块释放。对于“上传一个小程序、立即执行、执行完退出”的任务式模块，
这种模型具有以下优势：

- 分配次数少；
- 内存碎片风险较低；
- 不长期保留 ELF 节信息和模块管理元数据；
- 峰值 RAM 可以近似理解为输入缓冲区、模块运行内存和调用栈之和。

### 3.5 模块文件可以更紧凑

当前 Hello 示例的构建产物为：

- ELF `.o`：996 字节；
- ANL：696 字节。

在该示例中，转换后文件缩小约 30%。这是单个示例的结果，不代表所有模块都能获得相同
比例；实际大小取决于代码、静态数据、符号数量和重定位数量。

更小的模块文件可以减少 Flash、串口传输时间和接收缓冲区压力。

### 3.6 宿主接口最小且受控

当前 QEMU 示例只向模块导出：

- `printk`；
- `k_msleep`。

这种显式白名单不需要向模块暴露大量内核符号，具有以下特点：

- 模块 ABI 边界清晰；
- 固件无需保留大量导出符号名称；
- 降低模块误用内部接口的概率；
- 产品可以只提供实际需要的少量稳定 API。

对于宿主接口只有十几个函数的设备，这种机制通常比通用动态链接符号系统更轻。

### 3.7 集成和移植路径短

ANL Loader 以普通 Zephyr 应用代码存在，不要求修改 Zephyr 内核，也不要求设备端集成完整
LLEXT 子系统。基本工具链为：

```text
C 源码 -> GCC 编译为 ELF .o -> Python 转换为 .anl -> 上传 -> MCU 加载执行
```

当产品只支持固定 CPU 和固定 ABI 时，移植工作主要集中在架构编号、重定位转换、设备端
重定位修补、入口调用约定和导出符号表。

## 4. Zephyr LLEXT 更适合的场景

ANL 的轻量化来自功能收敛。出现以下需求时，应优先考虑 Zephyr LLEXT：

- 模块需要长期驻留；
- 需要按名称调用模块中的多个函数；
- 需要模块注册、遍历、查询和卸载；
- 需要构造函数、析构函数或 init/fini；
- 需要模块向系统或其他模块导出符号；
- 需要用户态、内存域或更完善的隔离机制；
- 需要标准 ELF 工具链和 Zephyr LLEXT EDK；
- 需要在多个 Zephyr 架构和平台上维护同一扩展框架；
- 希望直接跟随 Zephyr 上游 LLEXT 的能力演进。

Zephyr LLEXT 提供 `llext_load()`、`llext_unload()`、`llext_find_sym()`、
`llext_call_fn()`、`llext_iterate()` 和 `llext_add_domain()` 等接口，其目标是构建通用的
动态扩展子系统，而不是把一次性模块加载路径压缩到最小。

## 5. 当前 ANL 原型的边界

当前实现仍属于最小原型，使用时应明确以下限制：

- 初始方案文档以 RV32I 为目标，当前可运行 QEMU 示例实际使用 ARM Thumb-2/Cortex-M3；
- 当前只支持少量 ARM 重定位类型；
- 节基址数组最多记录 16 个节；
- 示例输入二进制缓冲区为 8192 字节；
- 当前只有单入口执行模型；
- 模块入口返回后内存立即释放，不能继续使用其中的数据或函数；
- 没有用户态隔离，模块以原生代码方式执行；
- CRC-32 只能检测数据损坏，不能替代数字签名和可信启动；
- 面向恶意输入时，还需要加强节偏移、长度、重定位位置和入口范围校验；
- 当前符号解析为字符串线性查找，适合小型导出表，不适合数百个符号。

这些限制多数是轻量化取舍，而不是 LLEXT 已有能力上的优势。

## 6. 推荐项目定位

对外描述 ANL Loader 时，建议使用以下定位：

> 面向资源受限 MCU 的最小原生模块加载器：通过 PC 端预处理和精简 ANL 格式，将设备端
> Loader 控制在约 1 KB 代码量级，仅保留装载、必要重定位、受控符号解析和入口执行。

典型应用包括：

- 串口动态下发小程序；
- 设备诊断和产测模块；
- 小型算法热更新；
- 上传后立即运行的一次性任务；
- 固定硬件和固定 ABI 产品；
- Flash/RAM 紧张且不需要完整插件生命周期的设备。

最终可以将两种方案概括为：

> **ANL 优先最小资源占用、简单性和可控性；LLEXT 优先标准化、通用性和完整生命周期。**
